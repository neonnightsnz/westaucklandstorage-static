# Stage 12: Programmatic SEO (Pages at Scale)

> **Execution role: Conditional — skip by default.** Run this **only** when the
> business needs more than roughly 10 pages sharing one repeating keyword
> pattern. If it does not, do not open this stage.

**Goal:** generate many similar pages from a template and a dataset — without
creating thin content, doorway pages, or a cannibalisation problem.

**When to use this stage:** only when you need more than roughly 10 pages that
share one repeating keyword pattern. For a typical single-location trade
business, Stage 4 is enough — do not open this stage to look busy.

> **Default answer is no.** The single most common programmatic SEO failure is
> generating hundreds of pages nobody searches for. Better 100 great pages
> than 10,000 thin ones.

## The six core principles

1. **Unique value per page** — every page must offer something specific to that
   page. Swapping a variable in an otherwise identical template is the failure
   mode, not the method.
2. **Proprietary data wins.** Data defensibility, strongest first:
   1. Proprietary (you created it)
   2. Product-derived (generated by your users or jobs)
   3. User-generated (your community)
   4. Licensed (exclusive access)
   5. Public (anyone can use — weakest)
3. **Clean URL structure** — subfolders, not subdomains. Subfolders consolidate
   authority; subdomains split it.
4. **Genuine search intent match** — the page must actually answer the query.
5. **Quality over quantity.**
6. **Avoid penalties** — no doorway pages, no keyword stuffing, no duplicate
   content.

## Step 1: Identify the playbook

Match the repeating pattern to one of the 12 playbooks. Full detail and
value-requirements per playbook: `references/programmatic-playbooks.md`.

| Playbook | Pattern | Example |
|---|---|---|
| Templates | "[type] template" | "resume template" |
| Curation | "best [category]" | "best website builders" |
| Conversions | "[X] to [Y]" | "$10 USD to GBP" |
| Comparisons | "[X] vs [Y]" | "webflow vs wordpress" |
| Examples | "[type] examples" | "landing page examples" |
| Locations | "[service] in [location]" | "dentists in austin" |
| Personas | "[product] for [audience]" | "crm for real estate" |
| Integrations | "[A] [B] integration" | "slack asana integration" |
| Glossary | "what is [term]" | "what is pSEO" |
| Translations | Multi-language content | localized pages |
| Directory | "[category] tools" | "ai copywriting tools" |
| Profiles | "[entity name]" | "stripe ceo" |

Choose by asset:

| If the business has… | Consider… |
|---|---|
| Proprietary data | Directory, Profiles |
| Integrations / partners | Integrations |
| Design or creative output | Templates, Examples |
| Multiple customer segments | Personas |
| Local presence | Locations |
| A tool or calculator | Conversions |
| Real expertise | Glossary, Curation |
| Competitors worth comparing | Comparisons |
| International reach | Translations |

**Local service businesses will almost always land on Locations, Personas,
Glossary, Comparisons or Examples.** Layering is allowed and often stronger
(e.g. Locations + Personas: "commercial marine electricians in Auckland").

## Step 2: Research the keyword pattern

- **Structure:** what repeats, and what are the variables?
- **Combinations:** how many genuinely exist? (variables × valid values)
- **Demand:** aggregate volume across the pattern, and the spread between head
  and long tail.
- **Trend:** growing, flat, or declining.
- **Cannibalisation:** does each page target a distinct query, or will two
  pages compete for the same intent?

Reject any combination with no real search demand. Volume is not the goal —
qualified demand is.

## Step 3: Audit data before generating

For each page you need data that is (a) accurate, (b) current, and (c)
specific to that page. Record:

| Field | Source | Owner | Update frequency | Tier (1–5) |
|---|---|---|---|---|

Rules:

- Never generate from data you cannot verify.
- Never publish an unverifiable price, rating, service area or credential.
- If the only available data is public and generic, the pages will be thin —
  stop and fix the data first.
- Outdated or incorrect data is worse than no page.

## Step 4: Design the template

Every generated page needs:

1. Header carrying the target keyword naturally
2. A **unique intro** — not the headline reworded
3. Data-driven sections specific to that page's variables
4. Conditional content that changes with the data (do not render identical
   blocks everywhere)
5. Original insight or analysis for that page
6. Related pages / internal links
7. A CTA appropriate to the intent

### Uniqueness test

If you can swap two pages' variables and the content reads identically, the
template has failed. Minimum differentiation for local pages is set by the
Stage 4 gates — 60%+ unique content per primary location page.

## Step 5: Architecture — hub and spoke

- **Hub:** one index/category page listing and linking to every spoke.
- **Spokes:** the individual generated pages.
- **Cross-links:** related spokes link to each other where genuinely useful.
- **Breadcrumbs** with structured data.
- **No orphan pages** — every page reachable from the main site.
- Every page in the XML sitemap.

See Stage 4 for the full internal-linking map and URL conventions.

## Step 6: Indexation strategy

- Prioritise high-volume patterns; launch the strongest pages first.
- **Noindex genuinely thin variations** rather than letting thousands of weak
  pages dilute crawl budget.
- Segment the XML sitemap **by page type** so indexation can be diagnosed per
  section.
- Watch crawl budget: 500 pages may be fine on an authoritative domain and
  impossible on a new one.
- Resolve any conflicting `noindex` / canonical signals before launch.

### Diagnosing "pages are not being indexed"

Work in this order:

1. **Thin content** — do the pages offer unique value, or template + keyword?
   This is the cause far more often than anything technical.
2. **Discoverability** — are they linked from a hub and from the main site?
3. **Sitemap** — included, valid, submitted, and free of non-canonical URLs?
4. **`robots.txt`** — is anything important blocked?
5. **Indexability** — correct status codes and self-referencing canonicals?
6. **Site authority / crawl budget** — is the domain strong enough for the
   volume attempted?

Google may decline to index thin pages regardless of how correctly they are
technically set up. Content quality is the fix, not a resubmission.

## Pre-launch checklist

- [ ] Playbook identified and demand validated per page
- [ ] Every combination has real search demand
- [ ] Data is accurate, current and defensible
- [ ] Each page provides unique value (uniqueness test passed)
- [ ] Unique title and meta description per page
- [ ] Correct heading structure; one H1
- [ ] Schema implemented where it adds meaning
- [ ] Page speed acceptable on mobile
- [ ] Hub page exists and links to every spoke
- [ ] Related pages interlinked; no orphans
- [ ] In the XML sitemap; crawlable; no conflicting noindex
- [ ] No cannibalisation between generated pages
- [ ] CTA on every page, matched to intent
- [ ] Owner has verified all claims and data

## Post-launch monitoring

Track: indexation rate, rankings, traffic, engagement, conversion — by page
type, not just site-wide.

Watch for: thin-content warnings, ranking drops, manual actions, crawl errors,
and pages indexed but never shown (usually a quality signal).

## Structured data for scaled pages

- Location pages: `LocalBusiness` + `areaServed`, with `branchOf` to the
  homepage `Organization`
- Comparison pages: keep it honest — do not mark up competitor data you have
  not verified
- Glossary pages: `DefinedTerm` where appropriate
- Never recommend `HowTo`; FAQPage rich results are retired (see Stage 11)

## Common mistakes

- **Thin content** — swapping a city name in otherwise identical content
- **Keyword cannibalisation** — multiple pages chasing one query
- **Over-generation** — pages with no search demand
- **Poor data quality** — outdated or incorrect information
- **Ignoring UX** — pages built for Google rather than for people

## Output

A strategy document (opportunity analysis, implementation plan, content
guidelines) and a page template (URL structure, title/meta templates, content
outline, schema).
